# Limitations

Known limitations, kept current as milestones land. Every report's limitations and footprint sections are drawn from this list.

## Project state

- No collectors exist yet. Nothing in this repository has been run on Windows. See `docs/STATUS.md`.

## Footprint (CLAUDE.md A16)

The tool aims for zero intentional host writes. Windows can still record activity on its own, outside the tool's control:

- Prefetch entries and other execution artifacts for `Canaveral.exe`.
- NTFS last-access timestamp updates on files that are read, where enabled.
- WMI service activity (`wmiprvse.exe`) when WMI is queried.
- Windows Error Reporting files if the process crashes.
- Security and other event log entries generated by Windows.

- USB device records created when the drive is connected (USBSTOR and MountedDevices registry entries, `setupapi.dev.log`). These exist before the tool even starts.
- Paging file or hibernation file contents, which may hold pieces of the tool's memory.

These are disclosed, never suppressed or erased.

## Output destination (M2)

- The volume inspector's Windows code has only run on GitHub's windows-latest runner, which has no removable media. Removable and USB detection has not been checked on real hardware or a VM yet.
- Drives created with `SUBST`, and volumes whose GUID cannot be read, are refused, because the tool cannot confirm they are not the system volume.
- A USB volume mounted into a folder (instead of a drive letter) is refused when the path passes through the mount point, because it looks like a junction.
- Output to network shares is always refused, since writing there means network traffic from the tool.
- Free space is checked when the destination is chosen, not before every write. A write that runs out of space is handled as a destination failure (data kept in memory, alternate destination offered).
- If the output device disappears, temporary files already on it cannot be removed. The footprint review lists them as resources that may remain.
- Cleanup identifies the tool's own files by file ID plus size. On FAT32/exFAT, file IDs come from directory-entry positions, so a different file of exactly the same size and name in the same place would be indistinguishable. Cleanup only ever targets `.partial` files and empty directories the tool created, which limits the impact.
- The scan directory name (`scan_<UTC timestamp>`) contains no hostname, so a lost USB does not reveal which machine was scanned by its folder names alone. Report contents still do (see redaction, M12).

## Static enforcement is a guard, not proof

The lint rules in `.golangci.yml` catch the common ways to spawn processes, write to the host or open network connections. They cannot catch everything:

- APIs called by string name through `NewLazySystemDLL(...).NewProc("...")`.
- `windows.CreateFile` and similar open calls, whose read-versus-write intent sits in flag arguments.
- Writes through a file handle obtained some other way.
- Files excluded by build tags in both lint passes (only the host OS and `GOOS=windows` are linted).

The real guarantee comes from code review plus the Procmon and pktmon footprint audit (CLAUDE.md section 7.2).

## Evidence retention

- Memory usage is an estimate (fixed per-node and per-edge costs plus string lengths, and payload sizes when the payload reports one), not a measurement of the Go heap.
- The budget is enforced only when the engine calls `EnforceBudget` after a snapshot, so usage can exceed the budget by up to one snapshot's worth of evidence between calls.
- If an evicted fact is observed again, it starts a new node with a fresh count. The earlier observations survive only in the eviction summary.
- Protected evidence is never evicted, even when it alone exceeds the budget. This is reported, but memory is not capped in that case.

## Observation

- Snapshot polling cannot guarantee observing every connection. Short-lived connections between polls can be missed.
